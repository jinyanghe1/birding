## 3. 微信小程序可行性分析

### 3.1 结论

前端重写成本低（无框架债、单文件 56.3KB、7 个 tab 天然对应 7 个页面）；真正阻塞项是两个：**网络合规**（域名 + ICP 备案 + HTTPS，当前裸 IP + HTTP 直接不合规）与**鉴权方式改造**。包体积（主包 ≤2MB，重写后预计几百 KB~1MB）、流量（3Mbps/200GB 月对小家庭够用）均无压力。

### 3.2 技术难点逐项

| 难点 | 现状 | 小程序要求 | 方案 |
|---|---|---|---|
| 网络合规 | `http://124.223.171.149` 裸 IP | request 合法域名必须 **HTTPS + ICP 备案**、不能用 IP、端口规则严格 | 注册域名 → ICP 备案（约 1-2 周）→ 443 证书 → Nginx |
| 图片鉴权 | `/api/photos/{id}` 要 `X-API-Key` header | `<image>` 不能带 header；`uploadFile`/`downloadFile` 也不能 | 改 query token（签名 URL，带过期）或 COS 临时密钥 |
| 登录体系 | API Key 永久有效、无过期 | 应改登录态 | 微信登录 unionid 绑定 users 表，token 有过期；妈妈已有 key 需绑定流程 |
| DOM 依赖 | 全部 innerHTML + querySelector + Leaflet | 无 DOM，需 WXML/setData 重写 | 7 tab → 7 页面；地图换原生 `<map>` 组件（OSM/百度瓦片不可直接用） |
| 包体积 | index.html 56.3KB | 主包 ≤2MB、总计 ≤30MB | 无压力 |
| 视频 | 相册可传 mp4，`/thumb` 回退原图 | video 组件需封面 | 服务端 ffmpeg 抽帧（逻辑已有） |

### 3.3 迁移 / 同步难点

- **数据双写**：小程序上线后与 Web 并存需双维护；建议小程序为唯一新前端，Web 逐步冻结。
- **图片迁移**：当前图走源站 Nginx 静态（无 CDN），原图+缩略图双份占 40GB 盘；迁小程序应转 COS+CDN（当前 <30MB/月流量，成本可忽略）。
- **账号体系**：现有 api_key 体系与微信 openid 的映射；邀请码+微信登录需合并为一条注册流。
- **审核**：UGC 相册需接内容安全接口（imgSecText/mediaCheck）；个人相册类目注意资质要求。
- **云开发 vs 自建**：CloudBase 云函数走内置通道免域名配置，但服务器 SQLite 数据需迁移；自建+备案数据不动、风险最小。**推荐自建 + 域名备案**，CloudBase 作远期选项。

## 4. 长程重构规划（每用户独立方案）

### 4.1 核心矛盾

核心 6 表**全局无用户维度**（observations 是全局共享的），而共享 5 表已多用户化。「每个用户独立解决方案」= 观测数据按用户隔离、鸟种字典共享。

### 4.2 三条路线对比

| 路线 | 模型 | 优点 | 缺点 |
|---|---|---|---|
| A 全局库+用户视图 | species 全局；observations/photos 加 user_id | 改造成本中；家庭共享靠显式授权 | 查询都要带 user 过滤，易漏 |
| B 完全隔离 | 每用户独立 DB/schema | 简单彻底 | 失去家庭共享；备份 N 份；无跨用户统计 |
| **C 家庭组混合（推荐）** | species 全局字典；observations 加 owner_id（默认私有、可授权家庭组）；相册按 group | 与 v2 模型演进路径最短；契合「多一个用户→相册对应关系」；家庭共享内建 | 需要一轮数据迁移 |

### 4.3 数据模型演进（路线 C）

```
users (+ group_id)
  └─> observations.owner_id（新增 + 索引；存量 516 条全归 owner）
species（全局字典，不变）
albums（owner_id 语义升级为 group_id）
album_photos（保留；全局 SHA256 去重保留）
cloud_photos（保留；可见性经 group 判定）
invites（升级：绑定 group 而非一次性 album_ids；新相册自动对组内可见）
id_queue（按用户分流，或维持全局 + 权限过滤）
```

关键决策点：① 存量 observations 归属迁移策略；② 邀请制从「一次性绑定 album_ids」改「绑定 group」；③ 识别队列的多用户分流。

### 4.4 分阶段 Roadmap

- **P0（本周）**：~~key 轮换~~（✅）→ scan 鉴权 → 上传白名单/下载 Content-Type → 相册 6 端点复活（P0-2）→ schema 重建迁移（P0-3）→ 前端注册端点（P1-10）→ TestClient 回归测试。
- **P1（2-3 周）**：相册正确性与卫生（P1-5/6/7/8/9）→ P2 性能与一致性 → 服务器定时备份落地（每天 3 点，长期挂账项）→ 本地 3 个 commit 推送 + 服务器代码同步。
- **P2（1-2 月）**：路线 C 数据模型重构（observations.owner_id、group 模型、邀请制升级）→ Web 端按用户视图 → 权限矩阵测试。
- **P3（季度）**：域名 + ICP + HTTPS → 小程序前端（7 页面重写、微信登录、签名 URL 图片、内容安全）→ COS/CDN 图片迁移 → Web 冻结。
